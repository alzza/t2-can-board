# Chat Log 2026-05-05

## 세션 목표

오늘의 핵심 목표는 OTA 안전망을 한 단계 더 확장하는 것이었다.

사용자 요청:
- 새 펌웨어 OTA 후 3분 안에 사용 확인이 없으면 이전 펌웨어로 자동 복구.
- 그 이후에도 이전 펌웨어 복구완료 확인을 1분 안에 누르지 못하면, CAN 기능을 모두 제외하고 OTA 업로드만 가능한 펌웨어 복구모드로 진입.
- 복구완료를 확정하면 다음 부팅부터 복구모드 관련 숫자 카운트다운이 다시 나오면 안 됨.
- 구현 후 동작 방식 리포트와 오늘 기록을 남길 것.

## 설계 판단

처음 검토한 선택지는 두 가지였다.

1. 새 펌웨어 확인 실패 시 바로 OTA 전용 복구모드로 진입
2. 먼저 이전 파티션으로 롤백한 뒤, 이전 펌웨어 복구완료를 60초 안에 확인하지 못하면 OTA 전용 복구모드로 진입

최종 추천 및 승인된 안은 2번이다.

이유:
- 새 펌웨어의 웹/OTA 코드 자체가 깨졌다면, 같은 새 펌웨어 안의 복구모드도 깨질 수 있다.
- 이전 파티션으로 한 번 돌아가는 기존 안전장치를 유지하는 편이 1차 복구 가능성이 더 높다.
- 단, 이전 펌웨어도 불안정할 수 있으므로 60초 확인 실패 또는 확인 전 재부팅 감지 시 OTA 전용 복구모드로 들어가게 했다.

중요 제약:
- 이 2단계 복구확인 로직은 이전 파티션에 들어있는 펌웨어도 해당 로직을 포함하고 있어야 완전하게 동작한다.
- 기능이 처음 포함되는 1회차에는 이전 파티션이 구버전이면 60초 복구완료 확인 단계가 실행되지 않을 수 있다.
- 이후 양쪽 OTA 파티션에 이 로직이 들어가면 정상적으로 2단계 안전망이 작동한다.

## 구현 요약

### 1. OTA 상태 머신 확장

`ota_pending` NVS 상태를 아래처럼 확장했다.

| 값 | 의미 |
|---|---|
| `0` | 정상 상태 |
| `1` | 새 펌웨어가 기록됨, 다음 부팅에서 3분 확인 시작 |
| `2` | 새 펌웨어 3분 확인 진행 중 |
| `3` | 이전 파티션 롤백이 선택됨, 다음 부팅에서 60초 복구완료 확인 시작 |
| `4` | 이전 펌웨어 60초 복구완료 확인 진행 중 |
| `5` | OTA 전용 펌웨어 복구모드 |

추가된 시간 상수:
- 새 펌웨어 확인 창: `180000ms` = 3분
- 이전 펌웨어 복구완료 확인 창: `60000ms` = 1분

### 2. 새 펌웨어 확인 실패 후 이전 파티션 복구

기존 동작은 유지하되, 롤백 선택 시 바로 `ota_pending=0`으로 지우지 않도록 변경했다.

변경 후 흐름:
1. 새 펌웨어 업로드 성공 시 현재 실행 중인 파티션 label을 `ota_fallback`에 저장하고 `ota_pending=1` 기록.
2. 새 펌웨어 첫 부팅 시 `ota_pending=2`로 전환하고 3분 확인 타이머 시작.
3. 사용자가 새 펌웨어 사용을 확정하면 `ota_pending=0`, `ota_fallback=""`로 완전히 정리.
4. 사용자가 거절하거나 3분 타임아웃이 발생하면 이전 파티션을 boot partition으로 지정하고 `ota_pending=3` 기록 후 재부팅.
5. 새 펌웨어 확인 중 재부팅이 발생하면 `ota_pending=2`를 감지해 이전 파티션으로 복구.

### 3. 이전 펌웨어 복구완료 60초 확인

이전 파티션으로 부팅된 뒤 `ota_pending=3`을 보면 60초 확인 창을 시작한다.

흐름:
1. `ota_pending=3` 부팅 감지.
2. `ota_pending=4`로 바꾸고 60초 watchdog 시작.
3. 웹 상단에 `펌웨어 복구완료` 배너 표시.
4. 초 단위 카운트다운 표시.
5. 사용자가 `예, 복구완료 확인`을 누르면 `ota_pending=0`, `ota_fallback=""`로 정리.
6. 이 상태가 확정되면 다음 부팅부터 복구모드 관련 숫자 카운트다운은 나오지 않는다.
7. 사용자가 `OTA 복구모드로 전환`을 누르면 `ota_pending=5`로 저장하고 재부팅.
8. 60초 동안 응답이 없으면 `ota_pending=5`로 저장하고 재부팅.

추가 안전장치:
- `ota_pending=4` 상태에서 확인 전에 재부팅이 발생하면, 다음 부팅에서 이전 펌웨어도 불안정하다고 보고 바로 `ota_pending=5` 복구모드로 전환한다.
- 이로써 이전 펌웨어가 60초를 버티지 못하고 재부팅되는 경우 무한 복구확인 루프에 빠지지 않게 했다.

### 4. OTA 전용 펌웨어 복구모드

`ota_pending=5`이면 부팅 초기에 복구모드를 감지한다.

- MCP2515 A채널 초기화 안 함.

- `timeseriesStart()` 시작 안 함.
- `canAlertTask` 시작 안 함.
- `statusLogTask` 시작 안 함.
- `loop()`에서도 A채널 `appLoop()`를 호출하지 않고 대기만 수행.

`include/web/web_server.h` 변경:
- 복구모드에서는 웹서버가 최소 라우트만 등록한다.
- 유지되는 라우트:
  - `/`
  - `/api/status`
  - `/api/ota`
  - `/api/reboot`
  - captive portal용 `/generate_204`, `/hotspot-detect.html`
- CAN 스니퍼, 레코더, Nag 설정, 기능 토글, 로그 번들, BUS-OFF API 등은 복구모드에서 등록하지 않는다.

### 5. 복구모드 전용 최소 페이지

`include/web/web_ui.h`에 `WEB_RECOVERY_UI_HTML`을 추가했다.

복구모드 페이지는 아래만 제공한다.

- 펌웨어 파일 선택

의도:

- 불안정한 펌웨어 상태에서도 OTA 업로드 경로만 최대한 가볍게 유지.

### 6. 일반 대시보드 UI 변경

기존 새 펌웨어 확인 배너를 재사용해 상태별로 문구를 바꾸게 했다.

새 펌웨어 확인 중:

- 버튼:
  - `예, 복구완료 확인`

확정 후:

## 동작 방식 최종 요약

정상 OTA 성공 경로:
1. OTA 업로드
2. 새 펌웨어 부팅
3. 3분 안에 `예, 이 펌웨어 사용`
4. `ota_pending=0`으로 정리
5. 이후 카운트다운 없음

새 펌웨어 실패 후 이전 펌웨어 복구 성공 경로:
1. OTA 업로드
2. 새 펌웨어 부팅
3. 3분 안에 확인 없음 또는 사용자가 거절
4. 이전 파티션으로 재부팅
5. 60초 안에 `예, 복구완료 확인`
6. `ota_pending=0`으로 정리
7. 이후 복구확인 카운트다운 없음

두 펌웨어 모두 불안정한 경우:
1. 새 펌웨어 확인 실패
2. 이전 파티션으로 복구
3. 이전 펌웨어 복구완료 60초 확인 실패 또는 확인 전 재부팅
4. `ota_pending=5` 저장
5. OTA 전용 펌웨어 복구모드 부팅
6. CAN 기능 없이 웹 OTA 업로드만 제공

복구모드에서 새 펌웨어 업로드:
1. 복구모드 페이지에서 `.bin` 업로드
2. 업로드 성공 시 기존 OTA 흐름처럼 `ota_pending=1`
3. 새 펌웨어 부팅 후 다시 3분 확인 흐름 시작

## 남은 주의점

- 이 변경은 커밋하지 않았다. 사용자가 별도로 커밋을 요청하면 코드 파일만 커밋하고, 기존 선호대로 `docs/` 계열은 제외하는 것이 맞다.
- 복구모드 진입 자체는 NVS `ota_pending=5`에 의존한다.
- 이전 파티션이 이 로직을 포함하지 않는 구버전이면 60초 복구완료 확인 단계는 실행되지 않을 수 있다.
- 기능이 양쪽 OTA 파티션에 한 번씩 배포된 이후부터 2단계 안전망이 완전히 작동한다.
