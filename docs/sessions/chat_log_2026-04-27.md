## TX 백오프 지연 계산

### 왜 백오프가 BUS-OFF를 오히려 유발하는가

Tesla ID 880 프레임: **100Hz (10ms 주기)**

```
setTxBackoff(200ms) 발동 시:
  침묵 구간 = 200ms
  누락 에코 수 = 200 / 10 = 20프레임
  차량 에러 증가 추정 = 20 × 8 = +160 포인트
  기존 에러 카운터 = 128 (임계값 도달 시점)
  합산 = 128 + 160 = 288 → 256 초과 → BUS-OFF 확정

setTxBackoff(15ms) 발동 시 (04-24 수정 후):
  침묵 구간 = 15ms
  누락 에코 수 = 1~2프레임
  에러 증가 = +16 포인트
  합산 = 128 + 16 = 144 → BUS-OFF 미도달
  그러나 twai_get_status_info() 1ms 오버헤드 누적으로 여전히 불안정

백오프 없음 (현재 코드):
  하드웨어 자체 Error-Passive 처리 → 에코 계속 전송
  차량 ECU: 정상 응답 수신 → 에러 카운터 자연 감소 → 자동 복구
```

## 추가된 기능: TX 백오프 실험 토글

실차에서 원인을 직접 검증하기 위한 Web UI 토글 추가:

- **위치**: Web UI B채널 카드 하단
- **API**: `POST /api/tx-backoff` `{"enabled": true/false}`
- **기본값**: **OFF** (성공 코드 기준)
- **NVS 키**: `"tx_backoff"` (재부팅 후에도 유지)
- **ON 시 동작**: `tx_error_counter >= 128` 도달 시 `setTxBackoff(200ms)` 발동

**검증 순서:**
1. 차량 연결 후 `192.168.4.1` 접속
2. B채널 카드 → "🔬 TX 백오프 실험" 토글 **OFF** → BUS-OFF 0 확인
3. 토글 **ON** → 수분 내 BUS-OFF 카운터 증가 확인 (원인 증명)
4. 토글 **OFF** → BUS-OFF 멈춤 확인

## 핵심 교훈

### "근본 원인을 먼저 찾아라"
- 통신 불가의 최초 원인은 단 한 줄: `priority 10 → 4`
- 이것을 놓치고 BUS-OFF 처리 코드만 복잡하게 만든 것이 오버엔지니어링의 시작
- **다음번 통신 이상 시 첫 번째 체크리스트: NagTask 우선순위 확인**

### "성공 코드와 diff를 먼저"
- 동작하던 커밋(`af14200`)과 현재 코드를 먼저 비교했다면 훨씬 빨리 발견
- 복잡한 수정 전에 항상 `git diff <마지막_정상_커밋>` 실행

### "TX 백오프는 위험하다"
- TWAI 하드웨어는 ISO 11898에 따라 에러를 자체 처리한다
- 소프트웨어 TX 침묵은 Error-Passive 구간에서 역효과
- **원칙: 백오프 로직은 코드에 존재하지 않아야 한다**

### "ESP-NOW와 TWAI는 섞지 마라"
- `esp_wifi_set_channel()` 은 WiFi AP 연결을 끊는다
- Web UI TCP 세션 끊김 → "Web UI가 안 보인다"는 증상
- AP 모드 단독 사용 시 ESP-NOW는 불필요
