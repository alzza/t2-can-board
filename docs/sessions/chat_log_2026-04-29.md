## 오전 세션 (2026-04-29)

### 문제: "버스오프 발생 빈도 높으면 로그 다 차버리는 경우?" 위험도 분석

사용자 질문: 링 버퍼 16개 초과 시, 복수 이벤트 한 루프 스킵, 시간 overflow 처리 등 예외 상황은?

#### 분석 결과

**🔴 실제 위험 — 즉시 수정**

| 위험 | 원인 | 영향 | 수정 |
|------|------|------|------|
| **cJSON NULL crash** | `cJSON_CreateObject()` 실패 (heap 부족) 시 체크 없이 사용 → null deref crash | BUS-OFF 폭발 중 웹 요청 → 보드 리부트 | `if (!root)` 체크 + HTTP 500 반환 |
| **sinceLastMs 오버플로우** | `lastBusoffEventMs > ev.timestampMs` 조건식 — overflow(49.7일) 후 timestamp wrap하면 항상 false → sinceLastMs=0 | 1개월 이상 운행 시 로그 시간간격 정확도 저하 | unsigned wrap-around 활용: `(uint32_t)(ev.timestampMs - lastBusoffEventMs)` |

**🟡 구조적 한계 — 설계 수용**

| 상황 | 현황 | 타당성 |
|------|------|--------|
| 링 버퍼 16개 초과 덮어쓰기 | 오래된 이벤트 자동 삭제, `oldest = h - 16` 로직 정상 | ✅ API에서 oldest부터 최신까지만 JSON으로 반환하므로 정확함 |
| 복수 이벤트 한 루프 스킵 | seqNum이 불연속(gap) → 사용자가 로그에서 감지 가능 | ✅ 쿨다운 300ms ≥ 루프 1ms이므로 실질 발생 불가 |
| head uint32 overflow | 43억회 BUS-OFF → 현실 불가 | ✅ 무시 가능 |

   └── 쿨다운 조정? 배선 점검? 하드웨어 교체?

## 기술적 노트

### 왜 `maxRecoveryDurationMs`를 따로 저장하나?

**이유**: 단일 BUS-OFF → 복구 소요 45ms → 다음 BUS-OFF 전까지 87ms. 최대값은 87ms.

쿨다운이 1000ms면:
- 마진 = 1000 / 87 ≈ 11.5×
- 현실에서 "충분함"을 수치로 보여줄 수 있음.
- 반면 마진이 1.2×면 "위험" 경고 가능.

**대안**(고려했지만 선택 안 함):
- "최근 10개 BUS-OFF의 평균 복구시간" → 평균값도 의미있지만, **최악의 경우**(max)를 기준으로 해야 안전.
- "첫 BUS-OFF만 기준" → 환경 변화(온도, EMI)로 복구시간 변함.

**결론**: `maxRecoveryDurationMs` = 보수적이고 명확한 마진 판정.

### CSV vs TXT 형식 선택

**선택: TXT (구조화된 섹션)**

이유:
1. [1] 런타임 로그는 텍스트 → CSV 강제 변환 불필요
2. [2] BUS-OFF만 CSV → 3개 섹션 분리 출력이 명확
3. 사용자가 텍스트 에디터로 열기 쉬움 (메모장, Notes)
4. 웹 대시보드에서 파싱 불필요 (표시만 함)

**장점**:
- 한 파일에서 모든 정보 수집
- 시간 순서 추적 가능 (logRing 타임스탐프)
- AI 분석 시 구조 명확

### 질문 3: "Single Shot TX 켜면 지연드롭 상관없이 자동 처리되나?"

정리:
- **아님.**
- 6ms 지연드롭은 `send()` 호출 **전단**에서 동작 (늦으면 프레임 자체를 버림)
- Single Shot TX(`ss=1`)는 `send()` 호출 **후단**에서 충돌 시 재전송 금지

즉:
- 6ms 드롭 = 늦은 프레임을 사전에 차단
- SS = 충돌 후 재전송 폭주 억제

두 기능은 독립이며 동시에 필요할 수 있음.

---

### 질문 4: "충돌 시 재전송 안 하면 NAG 동작 안 되는 거 아닌가?"

핵심 트레이드오프:
- `ss=0` (OFF): 전달율 우세, 단 TEC 누적/BUS-OFF 리스크 증가
- `ss=1` (ON): TEC 보호 우세, 단 충돌 난 사이클은 포기(해당 echo 미스)

운영 우선순위:
- NAG 전달율 우선이면 기본은 `ss=0`이 맞음
- BUS-OFF/TEC 폭주 시 임시로 `ss=1` 전환해 안정화 및 원인 분리

---

### 질문 5: "재전송 안 한다는 게 1회만? 다음 루프면 초기화?"

정확한 동작 단위:
- **프레임 1건 단위**
- `ss=1`일 때도 루프가 다시 돌면 다음 신규 프레임은 또 1회 전송 시도

따라서:
- 시스템 전체 송신이 멈추는 것이 아님
- 충돌한 그 프레임만 재시도 없이 종료됨

| 1 | 스티어링 감지 | **SUCCESS** - 나그킬러 신호를 Tesla AP가 인정한 상태 |
| 2 | 나그 감지 | `require not detected` - 경고 상태 |
| 8 | 핸즈온 확인 | 핸들 감지 관련 보조 상태 |

신호 추출식:

```cpp
// ID 921, SG_ DAS_steeringHandsOnState : 42|4@1+
uint8_t dasState = (frame.data[5] >> 2) & 0x0F;
```

### 기능 1: ID 921 판정 결과를 시리얼과 웹에서 의미까지 표시

#### 변경 목적

기존에는 921 값이 수치로만 보이거나, 아예 현장에서 바로 해석되지 않아 "지금 성공 상태인지 / 나그가 다시 뜬 건지"를 즉시 판단하기 어려웠다.

#### 구현 내용

**`include/handlers.h` - `NagHandler`**

- ID 921 수신 시 `dasHandsOnStateRx`를 계속 동기화
- 값이 바뀔 때만 로그를 발생시켜 스팸 출력 방지
- `logRing.push()`와 `Serial.println()`를 동시에 호출해 웹/시리얼 양쪽에서 동일한 문맥 확보

추가된 출력 형태:

```cpp
[DAS921] 2→1  스티어링감지(SUCCESS!)
[DAS921] 1→2  나그감지(require not detected)
```

상태별 설명 문자열:

- `1` -> `스티어링감지(SUCCESS!)`
- `2` -> `나그감지(require not detected)`
- `0` -> `AP해제/정상`
- `8` -> `핸즈온확인`
- 그 외 -> `기타`

**`include/web/web_ui.h`**

- B채널 Nag 패널의 `DAS 921` 상태 셀에서 숫자만 보여주지 않고 의미를 함께 표기
- 색상 규칙도 현장 판독 기준에 맞게 정리

예시:

```text
✅ 성공(1)
⚠️ 나그감지(2)
정상(0)
핸즈온(8)
```

이 변경으로 실차 테스트 중 사용자는 다음 한 줄만 보고도 상태를 즉시 알 수 있게 됐다.

```text
[DAS921] 2→1  ✅ 스티어링감지(SUCCESS!)
```

즉, "방금 에코가 Tesla AP에 먹혔다"를 시리얼에서 바로 확인 가능해졌다.

### 기능 2: A채널 ID 82 (`EPAS3P_sysStatus`) Nag Killer 추가

#### 문제 인식

앞선 작업에서 B채널 ID 880/921 기반 진단은 강화됐지만, 사용자가 원래 요청했던 **A채널(bus 2/3) ID 82 기반 Nag Killer 본체**가 빠져 있었다.

사용자 지적 후, A/B 채널 경계를 유지하는 방식으로 A채널 전용 구현을 추가했다.

#### DBC 정합성

ID 82는 구조상 ID 880(`EPAS3S`)와 동일한 sysStatus 계열 프레임으로 취급할 수 있으며, 다음 필드를 동일 방식으로 사용했다.

```text
handsOnLevel       : 39|2@0+  -> frame.data[4] >> 6 & 0x03
sysStatusCounter   : 51|4@0+  -> frame.data[6] & 0x0F
sysStatusChecksum  : 63|8@0+  -> frame.data[7]
torsionBarTorque   : 19|12@0+ -> ((data[2]&0x0F)<<8)|data[3]
```

#### 구현 위치

**`include/handlers.h` - `HW3Handler` 확장**

변경 요점:

- `ids[] = {1021, 82}` 로 확장해 A채널 메인 핸들러가 ID 82도 직접 처리
- A채널 전용 PRNG/토크 워크 상태를 `HW3Handler` 내부에 별도 보관
- 실제 손 감지(`handsOnLevel != 0`) 상태에서는 개입하지 않도록 기존 B채널과 동일한 안전 가드 유지
- 카운터 증가, 체크섬 재계산, 에코 전송까지 A채널 안에서만 처리

핵심 내부 상태:

```cpp
uint32_t _aNagPrng = 0xCAFEBABE;
int16_t  _aNagTorqWalk = 2230;
uint8_t  _aNagExcFrames = 0;
uint16_t _aNagFramesUntilExc = 175;
```

이 값들은 B채널 구현과 유사한 **Stealth PRNG 기반 토크 워크**를 A채널에서도 재현하기 위한 것이다.
목표는 "항상 똑같은 값"이 아니라, 실제 사람이 살짝 토크를 주는 것처럼 보이는 자연스러운 패턴을 만드는 것이다.

#### 런타임 플래그 및 진단 카운터

**`include/can_helpers.h`**

신규 추가:

```cpp
inline Shared<bool> nagKillerARuntime{false};
```

진단 필드 추가:

```cpp
Shared<uint32_t> frames82{0};
Shared<uint32_t> nagAEchoCount{0};
```

의미:

- `frames82`: A채널에서 ID 82를 실제로 몇 번 받았는지
- `nagAEchoCount`: A채널 에코를 몇 번 발사했는지

즉, 실차에서 "토글은 켰는데 왜 안 먹지?" 상황이 생겨도

- **ID 82 자체가 안 들어오는지**
- **들어오지만 에코 조건이 안 맞는지**
- **들어오고 에코도 나갔는데 Tesla가 안 받아주는지**

를 나눠서 판단할 수 있게 됐다.

### 기능 3: 웹 UI에서 A/B Nag Killer 상호배타 제어

#### 요구사항

A채널 ID 82 Nag Killer와 B채널 ID 880 Nag Killer를 동시에 켜면, 서로 다른 버스에서 유사 목적 신호를 동시에 넣게 되어 원인 분석도 어려워지고 실차 동작도 복잡해진다.

따라서 **A와 B는 상호배타(mutual exclusion)** 로 동작하도록 정리했다.

#### 서버 측 구현

**`include/web/web_server.h`**

- NVS 키 추가: `nag_killer_a`
- 신규 API: `POST /api/nag-killer-a`
- B ON 시 A 자동 OFF
- A ON 시 B 자동 OFF

핸들러 동작 개념:

```text
/api/nag-killer   -> B채널 토글
  B=true  => A=false 저장

/api/nag-killer-a -> A채널 토글
  A=true  => B=false 저장
```

즉, 사용자가 어느 쪽을 켜든 나머지 하나는 즉시 해제되며, 이 상태는 NVS에도 함께 반영된다.

#### UI 측 구현

**`include/web/web_ui.h`**

신규 토글 행 추가:

```text
Autosteer Nag Killer A [A채널 ID 82 / bus2/3]
```

그리고 JS에서 공용 함수 `togSwitchMutex()`를 만들어,

- 자기 자신 토글 POST
- 성공 시 상대 토글 UI 즉시 OFF 반영
- 실패 시 체크 상태 롤백

까지 한 번에 처리하도록 정리했다.

결과적으로 사용자는 웹에서 다음 두 실험을 명확히 분리해서 비교할 수 있게 됐다.

1. **B채널만 ON** - 기존 ID 880 경로
2. **A채널만 ON** - 신규 ID 82 경로

### 기능 4: 실차 진단 흐름 정리

이번 변경 이후 실차 테스트 절차는 다음처럼 단순화되었다.

#### A채널 ID 82 테스트 절차

```text
1. 웹 UI에서 "Autosteer Nag Killer A" ON
2. 기존 B채널 Nag Killer는 자동 OFF 확인
3. 주행 중 ID 82 수신 여부 확인 (frames82 증가)
4. DAS 921 상태 변화 확인
5. 시리얼에서 [DAS921] 2→1 로그 확인
6. 웹 셀에서 ✅ 성공(1) 표시 확인
```

#### 성공 판정 기준

- `frames82`가 증가한다
- `nagAEchoCount`가 증가한다
- `DAS 921`이 `2 -> 1`로 바뀐다
- 시리얼에 `스티어링감지(SUCCESS!)`가 뜬다

이 네 가지가 동시에 맞으면, A채널 경로가 실제 차량에서 유효하다는 뜻이다.
