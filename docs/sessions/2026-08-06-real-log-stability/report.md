# 2026-08-05~06 실차 로그 안정성 분석

## 결론

현재 펌웨어의 CAN 송신·복구 구조를 다시 크게 바꿀 필요는 없다. B채널은 두 20분 시계열 480개 샘플 전체에서 RUNNING이었고 BUS-OFF, TEC, REC, TX Fail은 모두 0이었다.

Web UI에서 확인한 `3`은 BUS-OFF 횟수가 아니라 `BUS-ERR` 누적 3회다. BUS-OFF 전용 이력이 비어 있는 것은 이번 로그 기준으로 정상이다.

다만 A채널에는 부팅 14시간 22분 동안 RX 오버런 5회와 TX_FAIL Guard 27회가 남았다. 큐 드롭·BUS-OFF·TEC/REC 상승은 없어 즉시 구조 변경 사유는 아니며, 현 펌웨어를 기준선으로 유지하면서 증가율을 관찰하는 것이 타당하다.

## BUS-OFF와 BUS-ERR 교차 검증

| 항목 | 확인값 | 판정 |
|---|---:|---|
| B BUS-OFF | 0 | 실제 버스 분리 없음 |
| B BUS-ERR | 3 | 프로토콜 버스 오류 누적, BUS-OFF 아님 |
| B TEC 최대 | 0 | 송신 오류 누적 없음 |
| B REC 최대 | 첫 BUS_ERR 당시 18, 이후 0 | 일시적 수신 오류 뒤 정상 복귀 |
| B TX Fail | 0 | TWAI 송신 실패 없음 |
| B 드라이버 RUNNING | 480/480 샘플 | 두 시계열 전 구간 정상 |
| BUS_OFF 이벤트 | 0 | 이벤트 CSV에 없음 |
| RECOVERY 이벤트 | 0 | 복구가 실행되지 않음 |

`can_events 10.csv`에는 2026-08-05 17:48:16.330에 `BUS_ERR` 이벤트 1건이 있다. 당시 TEC 0, REC 18, 경보 플래그는 `0x00000200`이다. 한 번의 경보 처리 사이에 하드웨어 버스 오류 카운터가 3까지 증가할 수 있으므로 이벤트 행 1개와 `BusErr:3`은 모순이 아니다.

두 CANMOD 파일의 `[2] BUS-OFF 이벤트 로그`는 모두 `BUS-OFF 없음`이며 이벤트 CSV에도 `BUS_OFF`, `RECOVERY_SOFT`, `RECOVERY_OK`, `RECOVERY_FAIL`이 없다. 따라서 BUS-OFF 기록 루틴이 이번 주행의 3건을 누락한 것은 아니다.

## A채널 잔여 불안정 요소

- RX 오버런은 총 5회다. RX0 1회, RX1 4회이며 모두 TEC/REC 0 상태에서 발생하고 약 1초 뒤 EFLG가 해제됐다.
- 최근 20분 구간에서는 신규 오버런이 각각 0회와 1회였다.
- RAM 선회수 큐는 최대 3/32만 사용했고 드롭은 0이다. 현재 소프트웨어 큐 용량 부족 증거는 없다.
- 2ms 초과 폴링 공백은 부팅 누적 8회이며 최근 20분 구간에서는 새로 증가하지 않았다.
- A TX 하드 오류는 두 20분 구간에서 각각 79/4563(1.73%), 54/3364(1.61%) 증가했다. Guard는 1초 안에 TXFAIL 2회 이상일 때 15초간 개입했고 해당 구간에서 각각 6회, 3회 진입했다. 부팅 후 총 27회 모두 정상 해제됐다.
- 최종 A TEC/REC는 0, A BUS-OFF는 0, 현재 EFLG는 0이다.

따라서 A채널은 완전히 무오류라고 할 수는 없지만 보호 로직이 정상적으로 개입하고 복귀하고 있다. 기능 체감 끊김이 없다면 지금 Guard 임계값을 완화하거나 큐 크기를 다시 키우는 변경은 근거가 부족하다. Summon/TSLLC가 실제로 끊긴다면 다음 안정화 대상은 B채널이 아니라 A TXERR 원인 분리다.

## 권장안

1. 현재 펌웨어를 안정성 기준선으로 유지하고 CAN 송신·복구 로직은 이번 결과만으로 변경하지 않는다.
2. **적용 완료:** Web UI의 `BUS-ERR`에 `BUS-OFF 아님`을 명시하고 같은 영역에 `BUS-OFF 0 / BUS-ERR 3`을 함께 표시해 혼동을 없앴다.
3. **적용 완료:** 실제 BUS-OFF 진입 뒤 복구 성공·실패가 확정될 때 전용 이력이 정확히 한 행만 추가되고 중복 완료가 기록되지 않는 회귀 테스트를 추가했다.
4. A RX 오버런이 시간당 1회 이상 계속되거나 RAM 큐 드롭·TEC/REC가 1 이상 나타날 때만 다음 구조 변경을 검토한다.
5. 다음 로그에서도 A TX Guard 횟수와 실제 기능 체감 중단 시간을 함께 확인한다.
