# Chat Log 2026-05-01

## 세션 목표

오늘의 핵심 목표는 **NagKiller 동작을 바꾸지 않고 1차 관측만 추가**하는 것이었다.

사용자 의도:
- 실차 로그만 보고 `통신이 안 되는지`, `NagKiller가 gate에서 막히는지`, `echo를 시도했지만 늦게 버린 것인지`, `TWAI TX 큐/버스에서 막힌 것인지`를 구분하고 싶음.
- 테슬라가 지속적인 인젝션을 막는다는 이야기가 있으므로, 바로 제어 로직을 바꾸지 말고 먼저 관측값을 확보하고 싶음.
- 오늘 세션을 내일 이어서 볼 수 있도록 날짜별 로그 파일에 상세히 남기길 원함.

## 적용한 원칙

수정 전 확인한 기준:
- `.github/skills/karpathy-guidelines/SKILL.md`
- `.github/skills/tesla-can-2ch-stability/SKILL.md`
- `.github/skills/tesla-can-twai-diagnosis/SKILL.md`
- `.github/instructions/channel-boundary-2ch.instructions.md`
- ESP-IDF v4.4.8 ESP32-S3 TWAI 문서

중요한 해석:
- `twai_transmit() == ESP_OK`는 **실제 ACK 성공 보장**이 아니라, TWAI TX 큐에 들어갔거나 전송 시작에 성공했다는 뜻이다.
- 그래서 새 카운터 이름은 `txQueued` 성격으로 두었다.
- 실제 버스/ACK/충돌 문제는 기존 `bTxFailed`, `bBusError`, `bArbLost`, `TEC/REC`, `BUS-OFF`와 함께 봐야 한다.

## 구현 요약

이번 변경은 전부 관측 전용이다. Nag echo 조건, DAS gate, 6ms late-drop, PRNG 토크 프로필, BUS-OFF 복구 방식은 바꾸지 않았다.

### 1. B채널 진단 변수 추가

파일: `include/can_helpers.h`

`BChannelDiagnostics`에 아래 관측값을 추가했다.

- `echoAttemptCount`
  - runtime/handsOn/DAS gate를 통과해서 echo 후보가 된 횟수
  - late-drop으로 버려져도 attempt에는 포함
- `lastEchoAttemptMs`
  - 마지막 echo 후보 시각
- `echoAttemptGapMs`
  - 직전 echo 후보와의 간격
- `echoStreakCount`
  - 짧은 간격으로 연속된 echo 후보 횟수
- `echoStreakStartMs`
  - 현재 연속 echo 후보 구간 시작 시각
- `continuousEchoMs`
  - 현재 연속 echo 후보 구간 지속 시간
- `txQueued`
  - `twai_transmit()`이 `ESP_OK`를 반환한 누적 횟수
  - ACK 성공이 아니라 TX 큐 진입/전송 시작 성공 지표
- `lastTxQueuedMs`
  - 마지막 TX 큐 진입 성공 시각
- `lastTxFailMs`
  - 마지막 TX 큐 진입 실패 시각

### 2. NagHandler echo 시도 관측 추가

파일: `include/handlers.h`

`NagHandler::handleMessage()`에서 아래 위치에만 관측 로직을 넣었다.

흐름:
1. 921이면 DAS 상태만 갱신하고 return
2. 880이 아니거나 DLC 부족이면 return
3. runtime OFF면 `skipRuntimeOrInactive++`
4. handsOn != 0이면 `skipHandsOn++`
5. DAS 0/8이면 `skipDasState++`
6. DAS 0xFF이면 `nagFiredNoDas++`
7. 여기까지 통과한 뒤 `echoAttemptCount++`
8. 이후 기존 PRNG/echo frame 생성/6ms late-drop/send 흐름 유지

즉, `Attempt`는 “보내려고 했다”이고, `Echo`는 “driver.send()까지 호출했다”이며, `TxQ`는 “TWAI가 큐에 받았다”이다.

### 3. TWAI TX 큐 진입 관측 추가

파일: `include/drivers/twai_driver.h`

추가 getter:
- `getTxQueuedCount()`
- `getLastTxQueuedMs()`
- `getLastTxFailMs()`

`send()`에서:
- `twai_transmit(...) == ESP_OK`이면 `txQueuedCount_++`, `lastTxQueuedMs_ = millis()`
- 실패하면 기존 `txSuppressedCount_++`에 더해 `lastTxFailMs_ = millis()` 기록
- `driverOK_ == false` 상태에서 send가 호출돼도 실패 관측값을 남김

주의:
- 이 값은 ACK 성공이 아니다.
- 실제 실패 여부는 `bTxFailed`, `bBusError`, `bArbLost`, `TEC/REC`와 같이 봐야 한다.

### 4. 5초 런타임 로그 보강

파일: `src/main.cpp`

기존 `[B-NAG]`, `[B-GATE]`, `[B-DEEP]`는 유지하고 새 로그를 추가했다.

새 로그:

```text
[B-OBS] Try:+<dAttempt> TxQ:+<dTxQueued> Streak:<count>/<ms> Gap:<ms> AgeTry/Q:<ms>/<ms>
```

해석:
- `Try:+0`: gate를 통과한 echo 후보가 없음
- `Try:+N`인데 `Echo:+0`: 보통 late-drop 또는 그 전 보호 경로 확인
- `Echo:+N`인데 `TxQ:+0`: send 호출 후 TWAI 큐 진입 실패 가능성
- `TxQ:+N`인데 `TxFailed/BusErr/ArbLost` 상승: 큐 이후 버스/ACK/충돌 문제 후보
- `Streak/continuous`가 계속 커짐: 지속 주입 패턴 후보

## 실차 로그 해석표

### 통신 자체 문제

| 로그 신호 | 해석 |
|---|---|
| `B채널 RX=0`, `frameHz=0` | B채널 TWAI 수신 자체가 안 됨. 배선, TWAI 상태, BUS-OFF, Task alive 확인 |
| `RX>0`인데 `Filt=0` | B채널은 살아있지만 880/921이 안 들어옴. 필터 대상 ID/차량 버스 위치 확인 |
| `busoff_count` 증가 | TWAI가 BUS-OFF로 빠짐. TEC/REC, BusErr, GND/종단/ACK 문제 확인 |
| `RxMissed` 증가 | RX 큐가 밀림. B루프 폴링/웹 부하/태스크 지연 후보 |

### NagKiller gate 문제

| 로그 신호 | 해석 |
|---|---|
| `d880=0` 또는 `Verdict=NO_880` | 880 대상 프레임이 안 들어옴 |
| `d921=0`, `DAS=0xFF`, `NoDAS_Echo` 증가 | 921을 못 본 상태에서 fallback echo 중 |
| `Skip OFF` 증가 | NagKiller runtime OFF 또는 handler inactive |
| `Skip HO` 증가 | 차량이 이미 handsOn != 0으로 보고 있어 echo 불필요 |
| `Skip DAS` 증가 | DAS 상태 0/8이라 경고 상황 아님 |
| `Try=0`, `Echo=0` | gate에서 막힌 것. 위 skip 사유 확인 |

### Echo 시도 이후 문제

| 로그 신호 | 해석 |
|---|---|
| `Try 증가`, `Drop 증가`, `Echo 증가 없음` | 6ms late-drop 보호로 일부러 안 보냄 |
| `Try 증가`, `Echo 증가`, `TxQ 증가 없음`, `TxFail 증가` | driver.send() 호출 후 TWAI 큐 진입 실패 |
| `TxQ 증가`, `TxFailed/BusErr 증가` | 큐에는 들어갔지만 버스/ACK/물리 계층 문제 가능성 |
| `TxQ 증가`, `ArbLost 증가` | 동일 ID 송신 충돌 또는 arbitration loss 후보 |
| `Streak/continuousMs` 계속 증가 | 지속 주입 패턴 후보. 테슬라 차단 가설 분석 대상 |
