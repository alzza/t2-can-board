## 대화 흐름 요약

### 1. BUS-OFF 과잉 엔지니어링 검토 요청

**질문:** "지나친 오버엔지니어링이 적용된게 아닌지 검토하고 스크린샷에서 최대한 유추할 수 있는 문제점을 찾아서 수정안을 다시 찾아보자."

**스크린샷 분석 결과:**
- BUS-OFF 발생: 30회
- 복구(시도/성공/실패): 30/30/0
- 오류 피크 RX/TX: 0 / 240
- 수신 속도: ~100Hz, 에코 전송: 수신과 거의 1:1

**이전 수정의 과잉 엔지니어링:**
- `send()` 안에서 `twai_get_status_info()` per-call 호출 → 100Hz × syscall
- 임계값 5개 (192, 224, soft/hard 타이머, 큐 워터마크) 분기

**단순화 수정:**
- `send()`에서 상태 조회 제거, `nagKillerTask` 1ms 루프에서 CAN 규격 기반 임계값 128 감시
- `tx_error_counter >= 128` → `setTxBackoff(200ms)` 호출
- 임계값 128 = CAN ISO 11898-1 error-passive 진입점 (근거 있는 값)

### 2. ACK 실패가 진짜 원인이냐?

**질문:** "rx는 양호하고 tx할 때 tesla에서 ack를 못받은거라고?"

**설명:**
- Tesla ECU가 ACK를 안 보내는 게 아니라, 버스상 누군가 ACK를 못 보내는 순간이 생기는 것
- ECU 슬립/웨이크 전환, 또는 GND 미접지 시 절대 전압 기준 불일치
- 백오프 수정의 의미: BUS-OFF 자체를 막는 것 (TX 실패를 막는 게 아님)

### 3. NAG 동적/고정 모드와 BUS-OFF 관계

**질문:** "nag가 동적/고정일 경우에 달라질 수 있다고 본다."

**결론:**
- CAN 버스 레이어 관점에서 모드는 BUS-OFF에 영향 없음 (ACK는 하드웨어 처리)
- 단, 동적 모드의 excursion 구간(torqRaw ~2370)은 Tesla EPAS가 비정상 판단 → ECU 일시 보호 → ACK 없음 가능성은 이론상 존재
- 스크린샷은 고정 모드(0x08B6)에서도 BUS-OFF 30회 → 모드 무관한 다른 원인이 주범

### 4. GND 미접지 진단

**질문:** "t2-can 보드에 usb로 전원을 공급하고 a채널 b채널 gnd쪽에 서로 연결하면 되나?"

**설명:**
- A/B채널 GND 연결은 의미 없음 (보드 내부에서 이미 동일 GND 평면)
- 필요한 것: T2-CAN 보드 GND ↔ 차량 OBD GND (핀 4 또는 5)
- USB-C로만 전원 공급 + CAN H/L만 연결 + GND 선 미연결 = RX/TX 비대칭의 교과서적 증상

**OBD-II 핀:**
| 핀 | 신호 |
|---|---|
| 4 | 차량 섀시 GND |
| 5 | 신호 GND |
| 6 | CAN-H |
| 14 | CAN-L |

**질문:** "예전 코드 수정한 기록을 참고해서 보면 이전에는 버스오프 발생이 거의 없었거든?"

- 채널 전환 순간 CPU 인터럽트 레이턴시 급증 → TWAI ACK 수신 윈도우 놓침
- `initEspNowSender()`에서도 중복으로 `WIFI_AP_STA` 설정

### 6. 최종 수정 — WIFI_AP_STA → WIFI_AP

**수정 파일:**
- `include/web/web_server.h` line ~1579: `WiFi.mode(WIFI_AP_STA)` → `WiFi.mode(WIFI_AP)`
- `src/main.cpp` `initEspNowSender()`: `WiFi.mode(WIFI_AP_STA)` 제거, `esp_wifi_set_ps(WIFI_PS_NONE)` 유지

**이유:** ESP-NOW는 STA 접속 없이 AP 모드만으로 브로드캐스트 가능. STA 모드는 실제 WiFi 네트워크 접속 시에만 필요.

**빌드 결과:** SUCCESS (RAM 39.5%, Flash 43.5%)

### 8. 오리지널 ev-open-can-tools 2.4.0 비교

**질문:** "첨부된 ev-open-can-tools.2.4에는 bus-off 관련 부분과 현재 내 꺼랑 뭐가 틀린지 집중 분석"

**오리지널 2.4.0 vs 포크 (수정 전) 비교:**

| 항목 | 오리지널 2.4.0 | 포크 (수정 전) |
|---|---|---|
| `BUSOFF_COOLDOWN_MS` | 1000ms | 200ms |
| 복구 방식 | `stop+uninstall+install+start` | `twai_initiate_recovery()` |
| mutex | `SemaphoreHandle_t mutex_` | 없음 |
| `read()` timeout | 0ms (non-blocking) | 1ms (blocking) |
| `read()` drain | 8프레임 루프 | 1프레임 |
| `send()` timeout | 2ms | 1ms |
| `rx_queue_len` | 32 | 64 |
| `tx_queue_len` | 16 | 32 |
| `driverInstalled_` 가드 | 있음 | 없음 |

**BUS-OFF 원인 4가지 규명:**

| 순위 | 원인 | 근거 |
|---|---|---|
| 🔴 1 | `twai_initiate_recovery()` 사용 | GND 미접지 시 RECOVERING 영구 고착 |
| 🔴 2 | `BUSOFF_COOLDOWN_MS=200ms` | 복구 후 200ms마다 재진입 → 카운터 30회 빠른 누적 |
| 🟠 3 | mutex 없음 | `driverOK_`/`lastRecovery_` 멀티스레드 비보호 |
| 🟠 4 | `read()` 1ms blocking + 1프레임 | RX 큐 드레인 지연 → 오버플로 위험 |

### 9. twai_driver.h 오리지널 2.4.0 방식으로 완전 재작성

**수정 요약:**

```
BUSOFF_COOLDOWN_MS:     200ms → 1000ms
복구 방식:               twai_initiate_recovery() → stop+uninstall+install+start
mutex:                  없음 → SemaphoreHandle_t mutex_
read() timeout:         pdMS_TO_TICKS(1) 1ms → 0 non-blocking
read() drain:           1프레임 → kReadDrainBudget=8 루프
send() timeout:         pdMS_TO_TICKS(1) → pdMS_TO_TICKS(2) 2ms
rx_queue_len:           64 → 32
tx_queue_len:           32 → 16
driverInstalled_ 가드:  없음 → stopAndUninstallLocked() 이중해제 방지
exactFilterIds_[]:      없음 → setFilters() 정확도 보정용 SW 필터 추가
recoveryInProgress_:    있음 → 제거 (불필요)
```

**포크에서 유지된 것 (오리지널에 없는 기능):**
- `getBusoffCount()`, `getRecovery*Count()`, `getLastBusOff*()` 등 진단 accessor
- `setTxBackoff()` — nagKillerTask tx_error >= 128 트리거용
- `getTxSuppressedCount()` / `isTxBackoffActive()`
- `reinitWithMode()` — 시뮬 NO_ACK 모드용 (main.cpp에서 미사용)
- `shutdown()` — 소멸자 훅

**빌드 결과:** SUCCESS (RAM 39.5%, Flash 43.5%)

**커밋:**
```
fix(twai): align BUS-OFF recovery with upstream ev-open-can-tools 2.4.0
ROLLBACK: git revert HEAD  OR  git checkout f08dce7 -- include/drivers/twai_driver.h
```
