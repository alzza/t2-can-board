## CSV 구조 검증

## 먹통 원인 후보

- 현재 `TsSample`은 332바이트이며 240샘플 전체 크기는 79,680바이트다.
- 통합 로그 처리기는 20분 버퍼를 저장할 때 `malloc(tsN * sizeof(TsSample))`로 최대 79,680바이트를 한 번에 추가 할당한다.
- 재부팅 후 통합 로그 섹션 3에서 확인된 free heap은 94,104바이트, 세션 최소 free heap은 40,116바이트다. 240샘플 스냅샷 할당이 성공하면 이론상 남는 free heap은 할당기 비용을 제외하고 약 14.4KB뿐이어서 TCP 전송 버퍼와 다른 Web 작업에 불리하다.
- 재부팅 직후에는 시계열이 4샘플뿐이어서 스냅샷 할당이 약 1.3KB에 불과했고 통합 로그 저장이 성공했다.
- Web UI는 통합 로그 링크를 누르면 백그라운드 상태·Nag 폴링을 성공 여부와 관계없이 180초 중지한다. 다운로드가 끝나도 화면이 3분간 갱신되지 않아 보드가 먹통처럼 보일 수 있다.
- 서버는 통합 로그 처리 중 같은 상태 API에 503을 반환하도록 되어 있고 HTTP 서버는 단일 처리 태스크이므로, 다운로드 전송이 지연되면 Web UI 응답도 함께 늦어진다.

따라서 이번 증상은 CSV 열 수 불일치보다 `대용량 순간 heap 할당 + 단일 HTTP 스트리밍 + 180초 UI 폴링 중지` 조합이 더 유력하다. 재부팅 전 Web health 카운터가 RAM과 함께 사라졌기 때문에 당시 실제 HTTP 실패 단계는 확정할 수 없다.

## 실차 CAN 결과

- 로그 범위는 재부팅 후 업타임 약 5.2~27.6초로, 실제 주행 구간은 포함하지 않는다.
- A채널은 부팅 직후 `EFLG=0x40`, RX0 오버런 1회가 있었고 1초 뒤 해제됐다. 이후 스냅샷까지 추가 오버런은 없다.
- RXB0/RXB1 누적 수신은 2,386/69, RAM 큐 최대 사용량은 2/32, 큐 드롭은 0이다.
- 루프 최대 공백은 1,590us이고 2ms 초과는 0이다.
- A채널 TX hard error, arbitration lost, abort, MERRF, TEC/REC, BUS-OFF는 모두 0이다.
- Summon과 TSLLC는 각각 45회 큐 등록·완료됐고 실패는 0이다.
- B채널 BUS-OFF, TEC/REC, bus error, TX fail, RX missed와 echo drop은 모두 0이다.
- 차량은 파킹 상태이고 AP 상태 1이므로 AP 전용 Nag가 주입하지 않고 `AP_BLOCK`으로 감시한 것은 의도한 동작이다.

## 이전 로그와 비교

- 2026-08-01 약 19분 55초 로그에서는 A RX 오버런이 300에서 680으로 380회 증가했고, 2ms 초과 공백은 7에서 11로 4회 증가했다.
- 새 로그에서는 부팅 직후 RX0 오버런 1회 뒤 약 22초 동안 재발하지 않았고 2ms 초과 공백은 0이다.
- 짧은 정차 로그라 개선 방향은 긍정적이라고만 판단할 수 있으며, 장시간 주행 안정화 성공으로 확정할 수는 없다.

## 권장 순서

1. 차량 CAN 로직을 더 바꾸기 전에 통합 로그의 79.7KB 일괄 할당을 제거하고 작은 배치 또는 샘플 단위 스트리밍으로 변경한다.
2. Web UI에 다운로드 진행 상태를 표시하고 180초 고정 정지를 짧은 안전 타이머와 페이지 복귀·포커스 시 즉시 재개 방식으로 교체한다.
3. 240샘플이 찬 상태에서 통합 로그를 연속 3회 저장해 Web UI 복귀와 heap을 확인한다.
4. 그 다음 15~20분 주행 및 AP 구간 로그를 수집해 RX0/RX1 오버런 증가율, 큐 드롭, 2ms 공백, TX hard error를 비교한다.
5. 이 로그를 받은 뒤 TX Guard 2단계 진행 여부를 결정한다.
