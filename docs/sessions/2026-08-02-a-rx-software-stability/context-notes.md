# 2026-08-02 A채널 RX 소프트웨어 안정화 컨텍스트 노트

## 확정 범위

- 차량은 Tesla HW3이다.
- CAN-A는 Summon/EU Unlock/TSLLC/ECE R79, CAN-B는 Nag Killer 전용 구성을 유지한다.
- HW3 ID `0x3FD` mux 1의 bit 19는 ECE R79 제한 해제, bit 46은 Summon 제한 해제로 유지한다.
- 이번 작업에서는 bit 19/46, mux, TSLLC bit 38/39, 기능 게이트와 송신 주기를 변경하지 않는다.
- TX Guard 단계 동작 변경은 새 실차 로그를 받은 뒤 검토하는 2단계 작업이다.

## 실차 로그 근거

- 2026-08-01 로그에서 A채널 BUS-OFF=0, TEC=0, REC=0이며 주된 경고는 RX 오버런이었다.
- 이벤트의 오버런 해석은 반복적으로 `RX1OVR=1`, `RX0OVR=0`을 보였다.
- 기존 MCP2515 필터 순서는 ID 921, 1016, 1021을 모두 RXB1 쪽 필터에 배치해 주차·소환 상태의 동시 프레임이 한 버퍼에 몰릴 수 있었다.
- 고정 1ms 태스크 양보와 CAN 태스크 안의 긴 상태 문자열 생성은 짧은 MCP2515 하드웨어 큐에 추가 공백을 만들 수 있었다.

## 적용 구조

- ID 1021은 RXB0 필터와 RXB1 복제 필터에 배치하고, ID 280/921/1016/390을 나눠 RXB1 단독 집중을 줄인다.
- CAN-A 루프가 시작되면 RXB0을 우선하여 RXB0/RXB1을 최대 4프레임씩 32프레임 RAM 큐로 선회수한다.
- 큐의 프레임 하나를 처리할 때마다 하드웨어 버퍼를 다시 비운다.
- CAN-B 프레임 하나를 처리할 때마다 A채널 루프를 다시 호출한다.
- CAN 전용 Core 1은 활동 시 50us, 유휴 시 100us만 짧게 대기하고 20ms마다 RTOS 1 tick을 양보한다.
- 5초 상태 로그 생성은 Core 0 전용 태스크가 담당한다.

## 새 진단값

- RXB0/RXB1별 누적 수신량과 오버런 수
- 실제 RX 선회수 프레임 수와 빈 폴링을 제외한 회수 배치 수
- 32프레임 RAM 큐 최대 사용량과 드롭 수
- 250us, 500us, 1ms, 2ms 초과 CAN 루프 공백 누적 수
- 마지막 오버런을 발견한 처리 단계

개별 A/B 시계열 CSV는 스키마 4다. 이벤트 CSV 스키마는 2로 유지한다.

## 다음 실차 합격 기준

- `a_rx_queue_drops=0`
- `a_rx0_overrun`과 `a_rx1_overrun`의 증가 속도가 이전 로그보다 뚜렷하게 감소
- RXB0/RXB1 수신량이 한쪽에 비정상적으로만 집중되지 않음
- A채널 BUS-OFF=0, TEC=0, REC=0, MERRF 증가 없음
- 1ms/2ms 초과 루프 공백 증가가 오버런 시점과 반복적으로 겹치지 않음
- ECE R79, Summon, TSLLC와 Nag Killer 기능의 기존 조건 및 동작 유지
