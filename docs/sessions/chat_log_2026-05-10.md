- 기존 차량에 현재 펌웨어를 OTA 업데이트하려고 하면 웹 UI가 "업로드 중..."에서 더 진행되지 않는다.
- OTA 업데이트 로직을 처음부터 다시 검토하고, 버그 가능성과 놓친 부분을 정리한다.

확인:
- 정상 UI와 복구모드 UI 모두 `XMLHttpRequest`에 `FormData`를 붙여 `/api/ota`로 전송한다.
- 서버 `otaHandler()`는 `req->content_len` 전체를 `Update.begin(req->content_len)`에 넘기고, `httpd_req_recv()`로 받은 바이트를 그대로 `Update.write()`에 기록한다.
- 서버 쪽에는 `multipart/form-data` boundary/header/footer를 파싱하거나 제거하는 코드가 없다.
- Arduino ESP32 `Update.write()`는 첫 플래시 바이트가 `ESP_IMAGE_HEADER_MAGIC`인지 검사한다. 실제 `firmware.bin` 첫 바이트는 `0xE9`이고, multipart 요청 첫 바이트는 boundary의 `'-'`가 된다.
- 현재 partition table은 `min_spiffs.csv`: `app0/app1` 각각 `0x1E0000`이고, 현재 `firmware.bin`은 921248 bytes라 공간 부족은 1순위 원인이 아니다.

판정:
- 가장 강한 원인은 UI와 서버 업로드 포맷 불일치다. UI는 multipart를 보내는데 서버는 raw firmware 바이너리를 기대한다.
- 이 상태에서는 `Update.write()`가 `UPDATE_ERROR_MAGIC_BYTE`로 실패할 수 있다.
- 서버가 요청 본문을 끝까지 소비하기 전에 에러 응답/연결 종료를 시도하면, 브라우저 쪽에서는 `onload`/`onerror`가 늦게 오거나 안 와서 "업로드 중..." 상태가 남을 수 있다.

의심 지점:
- 정상 UI와 복구모드 UI가 같은 `FormData` 업로드 코드를 중복 사용하므로, 둘 다 같은 문제를 가질 수 있다.
- UI에 `xhr.timeout`, `ontimeout`, `onabort`, `onloadend`가 없어 네트워크/응답 단절 시 버튼과 상태가 오래 고정될 수 있다.
- `/api/status` 폴링이 OTA 중에도 계속 돌지만, HTTP 서버가 단일 핸들러에서 OTA write를 수행하므로 상태 요청은 지연될 수 있다. 1순위 원인은 아니지만 OTA 중 폴링 중지는 안정성에 도움이 된다.
- OTA 성공 후 `ota_pending=1`, `ota_fallback`, `ota_expect_pt` 저장 및 재부팅 상태머신은 구조상 맞다. 다만 실제 업로드가 성공해야 의미가 있다.

다음 수정 후보:
- 가장 단순한 수정은 UI에서 `FormData` 대신 raw `.bin`을 그대로 전송하는 것이다. `xhr.setRequestHeader('Content-Type','application/octet-stream')` 후 `xhr.send(file)`로 바꾸면 서버의 현재 raw-body OTA 핸들러와 맞는다.
- 보조 수정으로 정상/복구 UI 양쪽에 `xhr.timeout`, `ontimeout`, `onabort`, `onloadend`를 추가하고, OTA 중 상태 폴링을 잠시 중지하는 방식을 검토한다.
- 서버 방어로 `Content-Type`이 multipart면 400 에러를 명확히 내거나, multipart 파서를 구현할 수 있다. 단순성과 안정성 기준으로는 raw upload로 통일하는 편이 우선이다.

검증:
- `min_spiffs.csv` 실제 partition 확인: `app0/app1` 각각 `0x1E0000`.
- `.pio/build/lilygo_t2can/firmware.bin` 확인: 921248 bytes, 첫 바이트 `0xE9`.
- Arduino ESP32 `Updater.cpp` 확인: 첫 바이트가 `ESP_IMAGE_HEADER_MAGIC`가 아니면 `UPDATE_ERROR_MAGIC_BYTE`로 abort.

- 실제 펌웨어 핫패스인 `include/handlers.h`의 `NagHandler::_handleModeB()`에는 `abs(steeringAngle) > 5°` 같은 조향각 절댓값 게이트가 없다.

- `|steering angle| ≤ 5°` 제한은 루트의 참조/실험 파일 `nag_kill_test_x2.cpp`에 있으며, 현재 PlatformIO `lilygo_t2can` 빌드 핫패스에는 들어가지 않는다.

- 현재 펌웨어 기준으로는 조향각 5도 제한을 완화하는 작업이 아니라, 새 조향각 상한 게이트를 추가하는 작업이 된다.
- 기본 5도, 상한 30도 파라미터를 추가하면 지금보다 보수적인 제한이 새로 생긴다. 30도로 올리면 원본 참조 알고리즘보다는 넓게 허용하지만, 현재 코드의 조향각 무제한 동작보다는 제한이 생긴다.
