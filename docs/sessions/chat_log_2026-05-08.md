## 2. B채널 TWAI 초기화 실패 원인 확정

실차 로그 핵심:
- A채널은 수신/처리가 살아 있음.
- B채널은 `TWAI=INIT`, `DriverOK=0` 상태.
- 즉 프레임 손실이나 BUS-OFF 이전 단계가 아니라, TWAI 드라이버 설치/시작 자체가 실패한 상태로 판단.

main 계열 코드와 비교한 결과:
- main refs에는 `g_config_.intr_flags = ESP_INTR_FLAG_IRAM` 강제 설정이 없었다.
- 현재 브랜치에는 unconditional IRAM interrupt flag가 들어가 있었다.
- Arduino-ESP32 2.0.17 / ESP32-S3 sdkconfig는 `CONFIG_TWAI_ISR_IN_IRAM`이 꺼져 있다.

수정:

```cpp

#endif
```

- Arduino-ESP32 기본 S3 환경에서는 IRAM flag를 설정하지 않아 `twai_driver_install()` 실패 위험을 제거.

## 추가 크로스체크: 왜 ESP_INTR_FLAG_IRAM을 넣었나

사용자 요청:
- 지난 대화에서 `ESP_INTR_FLAG_IRAM`으로 바꾼 분명한 이유가 있었을 것이므로 이력/의존성/현재 문제를 다시 교차 확인.

### 이력 확인

`git log -S 'ESP_INTR_FLAG_IRAM'` 결과, 해당 flag는 아래 커밋에서 도입되었다.

```text
8572167 feat: A/B CAN 통합 폴링 Core 1 + TWAI ISR IRAM 플래그
```

커밋 메시지상 의도:
- A/B CAN 통합 폴링을 Core 1 `nagKillerTask(prio 10)`로 모으는 과정.
- OTA/Flash write 중 cache-disable 구간에서도 TWAI ISR이 RX FIFO를 비우게 하려는 안정화.
- 즉 `ESP_INTR_FLAG_IRAM` 자체의 목적은 “실차 주행 중 일반 수신 안정화”라기보다 “Flash write/OTA 같은 cache-disable 구간 보호”였다.

문제였던 가정:
- 당시 주석에 `flag 자체는 미설정 환경에서도 안전하다`는 취지의 설명이 있었다.
- ESP-IDF v4.4.8 문서와 현재 Arduino-ESP32 S3 헤더는 이 가정을 지지하지 않는다.

### 공식 문서/헤더 확인

ESP-IDF v4.4.8 TWAI 문서의 IRAM ISR 조건:
- `CONFIG_TWAI_ISR_IN_IRAM`을 menuconfig에서 먼저 켠다.
- 그 다음 `twai_driver_install()`에 전달하는 `twai_general_config_t.intr_flags`에 `ESP_INTR_FLAG_IRAM`을 설정한다.

현재 Arduino-ESP32 2.0.17 / ESP32-S3 sdkconfig 확인:

```text
CONFIG_TWAI_ISR_IN_IRAM not defined in Arduino-ESP32 S3 sdkconfig
```

현재 프레임워크 헤더도 같은 전제를 명시한다.

```text
driver/twai.h: to use the ESP_INTR_FLAG_IRAM, the CONFIG_TWAI_ISR_IN_IRAM option should be enabled first.
```

### 실차 로그와의 대조

사용자가 제공한 `canmod_20260508_103312.txt`의 핵심:

```text
B-CH RX:0 ... TWAI:INIT
DBG ... TaskOK:1 | DriverOK:0
복구: 시도=18 성공=0 실패=18
BUS-OFF 없음
```

판정:
- B채널은 BUS-OFF로 죽은 것이 아니다.
- `nagKillerTask`는 살아 있다.
- TWAI 드라이버가 설치/시작되지 못해 `DriverOK=0` 상태가 반복된 것이다.
- 이 증상은 unconditional `ESP_INTR_FLAG_IRAM`과 현재 sdkconfig 불일치가 만드는 실패 양상과 맞는다.

### 최종 정책

현재 코드 정책:

```cpp
#if defined(CONFIG_TWAI_ISR_IN_IRAM) && CONFIG_TWAI_ISR_IN_IRAM
  g_config_.intr_flags = ESP_INTR_FLAG_IRAM;
#endif
```

의미:
- 기본 Arduino-ESP32 S3 빌드에서는 IRAM flag를 설정하지 않아 TWAI install 실패 위험을 제거.
- 만약 나중에 ESP-IDF 또는 커스텀 Arduino framework에서 `CONFIG_TWAI_ISR_IN_IRAM=y`로 빌드하면 원래 의도였던 OTA cache-disable 보호를 자동으로 되살림.

## 2026-05-08 19:20 KST - Web UI ID 880 수신률 표시와 age underflow 수정

사용자 추가 질문:
- 이전 결과 로그와 최신 스크린샷을 함께 보면 B채널이 정상이라고 하기에는 UI 표시가 찝찝하다.
- 로깅 시간을 길게 잡으면 더 정확히 판단할 수 있는지, 동의한다면 몇 분이 적당한지 문의했다.

판단:
- 이전 로그의 B채널 5초 집계는 `880:+500` 수준이라 ID 880 raw 수신은 정상 100Hz 근처로 보인다.
- `RX B`가 계속 증가하고 `TWAI RUNNING`, `TEC/REC=0`, `BusErr=0`, `TxFailed=0`, BUS-OFF 없음이면 물리 B 수신 불량보다는 UI/status 표시 문제가 더 유력하다.
- 스크린샷의 `4294967.3s`는 `/api/status` 응답 생성 중 `statusNowMs`를 먼저 잡은 뒤 CAN 태스크가 `lastFrameRxMs`를 더 최신 값으로 갱신하면서 unsigned underflow가 난 것으로 판단했다.
- 기존 UI가 `fresh=false`일 때 `frame_hz`를 0으로 덮어 `ID 880`의 마지막 측정률과 순간 fresh 상태를 섞어 표시했다.

수정:
- `include/web/web_server.h`에 `webSafeAgeMs()`를 추가해 age underflow를 0으로 clamp했다.
- A/B `frame_age_ms`, `loop_age_ms` 계산에 `webSafeAgeMs()`를 적용했다.
- `include/web/web_ui.h`에서 상단 `A OK 70ms`, `B NO FRAMES 4294967.3s` 같은 age 표시를 제거했다.
- UI가 `fresh=false`라는 이유만으로 `frame_hz`를 0으로 덮지 않게 했다.
- `FRAME RATE A/B` 라벨을 `ID 1021 RATE`, `ID 880 RATE`로 바꿔 어떤 ID의 Hz인지 명확히 했다.
- B 버스 상태와 ID 880 rate 색상 기준을 분리했다. `CAN BUS B`는 driver/fresh/TWAI 기준이고, `ID 880 RATE`는 80Hz 이상일 때 초록, 0이면 빨강으로 표시한다.
